# STEP 1：運営者アカウントを守る（パスワード変更＋2FA）

## 1-A. パスワードを変更する

### 手順

1. ブラウザで **https://rakuraku-kintai.vercel.app/superadmin/login** を開く

2. ログインする
   - メールアドレス：`biccuri5086@gmail.com`
   - パスワード：`2026super` を試す
     → 弾かれたら `Rakurakukintai 2026@` を試す（初期セットアップ時の候補）
     → **どちらも入れない場合は、この下の「ログインできないとき」へ**

3. ログインできたら **https://rakuraku-kintai.vercel.app/superadmin/password** を開く
   （または画面右上に並んでいるアイコンのうち、**南京錠のアイコン🔒**を押す。マウスを乗せると「パスワード変更」と出ます）

4. 3つの欄を埋める
   - **現在のパスワード**：さきほどログインに使ったもの
   - **新しいパスワード**：8文字以上（下の「良いパスワードの決め方」参照）
   - **新しいパスワード（確認）**：同じものをもう一度

5. **`パスワードを変更する`** を押す
   → 「パスワードを変更しました」と緑のチェックが出れば完了

6. **必ず確認**：一度ログアウトして、新しいパスワードでログインし直せることを確かめる

### 良いパスワードの決め方

- **他のサービスと絶対に使い回さない**（このアカウントだけの専用パスワード）
- 目安：英大文字・小文字・数字・記号を混ぜて12文字以上
  - 悪い例：`rakuraku2026`（サービス名から推測できる）
  - 良い例：`Nk7#mQz2vTr!Ls`（意味のない文字列）
- **保管場所**：ブラウザのパスワード保存 or パスワード管理アプリ（1Password / Bitwarden など）。
  紙のメモでも構いませんが、**リポジトリやDriveのテキストファイルには絶対に書かない**でください。

### ❌ ログインできないとき（パスワードを忘れた／どちらも通らない）

DBから直接リセットできます。

1. ローカルPCで新しいパスワードのハッシュを作る
   ```bash
   cd rakuraku-kintai
   node scripts/hash-password.mjs "ここに新しいパスワード"
   ```
   → `scrypt$16384$xxxx...` という長い文字列が出るのでコピー

2. Supabase → 対象プロジェクト → 左メニュー `SQL Editor` → `New query` に以下を貼り付け
   ```sql
   update super_admins
      set password_hash = 'ここに手順1でコピーしたscrypt$...の文字列',
          is_active = true
    where email = 'biccuri5086@gmail.com';
   ```
3. `Run` を押す → `Success` が出たら、新しいパスワードで `/superadmin/login` からログイン

> ローカルPCが使えない場合は、この作業だけ私（Claude）に依頼してください。
> ただし**パスワードそのものはチャットに書かないで**ください。ハッシュ生成だけ手伝います。

## 1-B. 2要素認証（2FA）を有効にする

パスワードが漏れても、スマホがなければ入れない状態にします。**Vercelの設定は不要です。**

### 事前準備：認証アプリをスマホに入れる

App Store / Google Play で以下のどれか1つをインストール（無料）：
- **Google Authenticator**（一番シンプル。迷ったらこれ）
- Microsoft Authenticator
- 1Password（すでに使っているなら）

### 手順

1. `/superadmin` にログインした状態で
   **https://rakuraku-kintai.vercel.app/superadmin/2fa-setup** を開く
   （または画面右上の**盾のアイコン🛡**を押す。マウスを乗せると「2段階認証」と出ます）

2. 「2FAは現在無効です」というオレンジの帯と、**QRコード**が表示される
   - QRが出ない場合 → STEP 0 のデプロイが終わっていません。0-2 に戻ってください

3. **STEP 1：認証アプリに登録**
   - スマホで認証アプリを開く → `+`（追加）→ **`QRコードをスキャン`**
   - パソコンの画面に出ているQRコードをスマホのカメラで読み取る
   - アプリに「RakurakuKintai-Owner」という項目が増え、**6桁の数字**が表示される
     （この数字は30秒ごとに変わります）
   - QRが読めない場合：画面の「シークレットキー（手動入力用）」をコピーし、
     アプリの「手動で入力」から貼り付け

4. **STEP 2：6桁コードで確認**
   - スマホに表示されている6桁の数字を画面の入力欄に入れる
   - **`確認する`** を押す → 「確認できました」と出ればOK
   - ❌ 失敗する場合：数字が切り替わる直前だった可能性があります。
     **新しい6桁が出るのを待ってから**もう一度入れてください

5. **`有効化する`** を押す
   → 「2FAを有効化しました」と出れば完了

6. **必ず確認**：ログアウトして、もう一度ログインしてみる
   - メール → パスワード → **6桁コードの入力を求められる** → 入力して入れればOK

### ⚠️ 一番大事な注意

**スマホを失くすと、あなた自身がログインできなくなります。** 必ずどちらかをやってください：

- **推奨**：QRの下にある「シークレットキー」を紙に書いて、家の安全な場所に保管
  （このキーがあれば新しいスマホに登録し直せます）
- または：認証アプリのクラウドバックアップを有効にする
  （Google Authenticator なら Googleアカウントとの同期をON）

**万一どちらもできずスマホを失くしたとき**の緊急解除：
Supabase → `SQL Editor` で以下を実行すると2FAが外れ、パスワードだけでログインできます。
```sql
update super_admins set totp_secret = null where email = 'biccuri5086@gmail.com';
```
（解除したら、必ずすぐ 1-B をやり直して再設定してください）

# STEP 2：DBのアクセス制限を確実にする（マイグレーション適用）

**なぜやるのか**：Supabase には `anon キー` という**ブラウザに丸見えになる鍵**があります。
本来この鍵では何も読めない設定（RLS有効・ポリシー0件）でなければいけません。
ところが初期セットアップ用のSQLに「全部許可」の開発用ポリシーを作る行が含まれていたため、
**本番DBにそれが残っている可能性**があります。残っていると、
誰でもブラウザから全社のスタッフ氏名・打刻・体調報告を読めてしまいます。

今回追加した `0006_rls_hardening.sql` が、残っていれば削除し、抜けていたRLSを塞ぎます。

> **検証済みです**：実際にPostgreSQLを立てて本番と同じスキーマを作り、
> 「開発用ポリシーが残った状態」を再現してこのマイグレーションを流し、
> anonキーから見える件数が **1件 → 0件** になること、
> アプリが使う service_role からは今まで通り読めることを確認しています。
> 何度実行しても安全（冪等）です。

## 2-1. 接続文字列（DATABASE_URL）を GitHub に登録する

### ① Supabase から接続文字列を取得

1. https://supabase.com → ログイン → **本番のプロジェクト**を開く
   - ⚠️ staging（`xkrwwrittprbpxlvucuu`）ではなく**本番**を選んでください。間違えると本番が直りません
2. 画面上部の **`Connect`** ボタンを押す
3. **`Session pooler`** のタブを選ぶ
   - ⚠️ `Direct connection` ではなく **必ず Session pooler**（GitHub ActionsはIPv6が使えないため）
4. 表示された文字列をコピー
   ```
   postgresql://postgres.xxxxxxxx:[YOUR-PASSWORD]@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres
   ```
5. **`[YOUR-PASSWORD]` の部分を、実際のDBパスワードに置き換える**
   - DBパスワードが分からない場合：
     Supabase → `Settings` → `Database` → `Database password` → **`Reset database password`** で新しく発行
   - 角カッコ `[` `]` も消して、パスワードだけを入れます

   置き換え後の例：
   ```
   postgresql://postgres.abcdefgh:MyRealPassw0rd@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres
   ```

### ② GitHub に Secret として登録

1. https://github.com/biccuri5086-hash/rakuraku-kintai を開く
2. **`Settings`**（リポジトリの設定。アカウント設定ではありません）
3. 左メニュー **`Secrets and variables`** → **`Actions`**
4. 緑の **`New repository secret`** ボタン
5. 入力する
   - **Name**：`DATABASE_URL` ← この名前でないと動きません（大文字・アンダースコア）
   - **Secret**：①で作った接続文字列をそのまま貼り付け
6. **`Add secret`**

> Secret は登録後は本人にも表示されません（それが正しい動作です）。
> 間違えたと思ったら `Update` で入れ直せます。

## 2-2. マイグレーションを実行する

### 方法A：GitHub の画面から実行（推奨・ターミナル不要）

1. リポジトリの **`Actions`** タブを開く
2. 左のリストから **`DB Migrate`** を選ぶ
3. 右側の **`Run workflow`** ボタン → ブランチが `main` になっていることを確認 → **`Run workflow`**
4. 少し待つと一覧に実行が現れるのでクリックして中を開く
5. ログに次の行が出れば成功
   ```
   接続OK
   未適用: 1件 → 0006_rls_hardening.sql

   === 適用: 0006_rls_hardening.sql ===
   → 成功

   全マイグレーション完了
   ```

**❌ うまくいかないとき**

| ログに出るメッセージ | 原因と対処 |
|---|---|
| `Secret DATABASE_URL が未設定のためスキップしました` | 2-1 ② が未完了。Secret名が `DATABASE_URL` になっているか確認 |
| `✗ エラー: password authentication failed` | パスワードの置き換えミス。`[YOUR-PASSWORD]` と角カッコが残っていないか確認 |
| `✗ エラー: getaddrinfo ENOTFOUND` / 接続できない | `Direct connection` の文字列を使っている。**Session pooler** の文字列に変える |
| `適用すべきマイグレーションはありません` | **すでに適用済みです。成功しています**。2-3 に進んでください |
| `✗ 失敗: 0006_rls_hardening.sql — ...` | 自動でロールバック済み（DBは変更されていません）。ログの `✗` の行を私に見せてください |

### 方法B：自分のPCから実行

ターミナルが使える場合はこちらでも構いません。
```bash
cd rakuraku-kintai
npm ci

# まず「何が適用されるか」だけ確認（DBは変更されません）
DATABASE_URL="postgresql://postgres.xxxx:パスワード@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres" npm run migrate -- --dry

# 問題なければ本適用
DATABASE_URL="postgresql://postgres.xxxx:パスワード@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres" npm run migrate
```
> 接続文字列は**環境変数で渡すだけ**にして、ファイルに保存しないでください。

## 2-3. 正しく直ったかを確認する（ここが一番大事）

1. Supabase → 対象プロジェクト → 左メニュー **`SQL Editor`** → **`New query`**
2. 以下を貼り付けて **`Run`**

```sql
-- ① 残っているポリシー（0行であること）
select tablename, policyname
from pg_policies
where schemaname = 'public';
```

**期待する結果：`Success. No rows returned`（0行）**

3. 続けて、もう1つ確認

```sql
-- ② RLSが無効なテーブル（0行であること）
select tablename
from pg_tables
where schemaname = 'public' and rowsecurity = false;
```

**期待する結果：`Success. No rows returned`（0行）**

### 判定

| 結果 | 意味 |
|---|---|
| ①②とも **0行** | ✅ **完了。anonキーでは何も読めない、正しい状態です** |
| ① に行が出る | ❌ ポリシーが残っています。2-2 が実行されていません。ログを確認してください |
| ② に行が出る | ❌ RLSが無効なテーブルがあります。出てきたテーブル名を私に教えてください |

> 「0行」は一見エラーのように見えますが、**このケースでは0行が正解**です。
> 「誰にも許可を出していない ＝ service_role（アプリ）だけが通れる」という意味になります。

## 2-4. アプリが壊れていないか確認する

RLSを締めた後、アプリが今まで通り動くことを確認します（service_role は RLS を迂回するので影響ないはずですが、念のため）。

1. https://rakuraku-kintai.vercel.app/api/health → `{"ok":true,"db":"up"}`
2. `/superadmin` にログイン → 会社一覧が表示される
3. `/admin/login` に会社の管理者でログイン → ダッシュボードにスタッフが表示される
4. `/admin/payroll` を開く → 給与プレビューが表示される

いずれかで「データが0件になった」場合は、すぐ連絡してください（RLSの締めすぎです）。
