## 1. バックアップが実際に存在するかの確認

1. Supabase → 対象プロジェクト（本番）→ 左メニュー `Database` → `Backups`
2. 一覧に日次バックアップが並んでいるか確認する
   - 並んでいる → OK。直近の日付が「今日から1日以内」になっているか確認して完了
   - 並んでいない・空 → Pro Planになっているか`Settings → Billing`で確認。Pro Planなのに空の場合は
     Supabaseサポートに問い合わせが必要（自動で溜まるまで待つのは非推奨）
3. 可能なら、その場で `Create backup`（手動バックアップ）も1回実行しておく

## 2. リストア訓練の実施（本番データは使わない）

RUNBOOK（`運用手順書_RUNBOOK.md` 3章）の手順を、**新規に作るstaging用プロジェクト**に対して行います。
本番プロジェクトには絶対に「誤って壊す」操作をしないよう、対象プロジェクトを毎回指差し確認してください。

### 2-1. staging用Supabaseプロジェクトを新規作成
1. Supabase → `New project` → 名前は分かりやすく（例：`rakuraku-kintai-staging`）
2. 作成後、`db/staging-bootstrap.sql`（本リポジトリ内）を SQL Editor で実行し、最低限のテーブルとseedデータを投入
3. `TODO_次にやること.md` の「A. ステージング環境の完成」の手順1〜5に沿って、VercelのPreview環境変数
   （`NEXT_PUBLIC_SUPABASE_URL`・`NEXT_PUBLIC_SUPABASE_ANON_KEY`・`SUPABASE_SERVICE_ROLE_KEY`）を
   この新プロジェクトの値に更新し、Preview環境をRedeploy

### 2-2. 練習用の「事故」を起こす
- staging環境で、適当なテーブルの行を1つ削除するなど、軽微な「事故」を意図的に起こす

### 2-3. RUNBOOK 3章の手順で復元する
1. Supabase（**stagingプロジェクトであることを再確認**）→ `Database` → `Backups`
2. 直近の復元点を選び `Restore`
3. 復元後、staging環境の `/api/health` が `db:up` になるか確認
4. 消したはずのデータが戻っているか確認

### 2-4. 結果を記録
