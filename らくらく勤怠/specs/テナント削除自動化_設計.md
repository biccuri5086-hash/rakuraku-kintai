## 0. 現状把握（実装前に確認した事実）

### 0-1. 危険な運用は2箇所ある
「本番DBに手動アクセスしてDELETEする」運用手順（`specs/運用手順書_RUNBOOK.md` 6.5章、前回追加）
に加えて、**既にアプリ内に即時・不可逆の物理削除APIが存在する**：

- `DELETE /api/superadmin/companies/[id]`（`src/app/api/superadmin/companies/[id]/route.ts`）
  会社名の再入力による二重確認はあるが、**確認が通った瞬間に `companies` 行を物理削除**しており、
  猶予期間もロールバックの余地もない。今回はこちらも合わせて直す。

### 0-2. スキーマは既にCASCADE設計になっている
`companies.id` を参照する子テーブルは、**新しいテーブルも含めて全て `on delete cascade`**
（`MULTITENANT_FIX_CASCADE.sql` および `PHASE_A/B/C/D` の各マイグレーションで統一済み）。
唯一の例外が `admin_audit_log`（`on delete set null`）で、これは**監査ログを会社削除後も
残すための意図的な設計**（コメントにも明記あり）。

→ **`delete from companies where id = ?` を1回実行するだけで、子テーブルは自動的に全て
物理削除される。** 個別テーブルを手作業で回る物理削除ロジックは不要（すでにDB側で担保済み）。

### 0-3. 「論理削除」の受け皿も既にある
`companies.status` は `'active' | 'trial' | 'suspended' | 'cancelled'` のenumで、
**`cancelled` は既存の値**。しかも以下2箇所は**既に `cancelled` を弾いている**：
- `/api/admin/login`（管理者ログイン拒否）
- `/api/me/register`（新規スタッフ登録拒否）

一方、**以下は `status` を見ておらず、解約後も動いてしまう**（要修正）：
- `/api/me/clock`（打刻）
- `/api/me/condition`（体調報告）
- `/api/me/gps`（位置情報更新）
- 一度発行された管理者セッション（`rk_tenant_session`）は署名付きトークンで**7日間、
  DBの `status` を再チェックしない**ため、解約後も期限まで管理画面を使えてしまう

### 0-4. RLSについての重要な前提（設計上の訂正）
要件には「既存のRLSポリシーを修正し、論理削除されたデータが見えなくなる状態を担保する」と
ありますが、**本アプリのアクセスは全て `service_role` 経由**であり、`service_role` は
Postgresの仕様上**RLSポリシーを常にバイパスします**（ポリシーをどう書いても効果がありません）。
`AGENTS.md` にも明記の通り、本プロジェクトの「見えなくする」担保は**アプリ層の責任**です。
→ 本設計では、RLSポリシーの追加ではなく、**上記0-3の「弾く」チェックを漏れなく揃えること**を
「見えなくする」担保の実体とします。

## 1. 設計方針（3本柱）

### 柱A：論理削除（解約）— `cancelled_at` の追加とチェックの徹底

**スキーマ変更**（新マイグレーション `0007_tenant_cancellation.sql`、additive）
```sql
alter table companies add column if not exists cancelled_at timestamptz;
create index if not exists idx_companies_cancelled_at on companies(cancelled_at)
  where cancelled_at is not null;
```

**解約の起点を一本化**：`PATCH /api/superadmin/companies/[id]` で `status` を `cancelled` に
変更したときだけ `cancelled_at = now()` を自動セット、`cancelled` 以外に変更したときは
`cancelled_at = null` に戻す（誤って復活させた場合に30日カウントが残らないように）。

**「見えなくする」チェックを4箇所に追加**（既存の2箇所と合わせて全経路を揃える）：
1. `/api/me/clock`・`/api/me/condition`・`/api/me/gps` — `user_profiles` から引いた
   `company_id` で `companies.status` を確認し、`cancelled` または `suspended` なら
   403（「このアカウントはご利用いただけません」）を返す。
2. `getTenantContext()` / `requireTenantContext()`（`src/lib/tenant-context.ts`）—
   **ここに一元化するのが本筋**。毎回DBを引く分わずかにコストは増えるが、個別ルートに
   チェックを書き漏らすリスクを構造的に無くせる。会社が `cancelled`/`suspended` になった
   瞬間から、既存セッションが残っていても即座に全 `/api/admin/*` が401/403になる。

**既存の即時物理削除APIを解約フローに統合**：
`DELETE /api/superadmin/companies/[id]` は**物理削除ではなく「論理削除（解約）」を行う**よう
挙動変更する（`status='cancelled'`, `cancelled_at=now()` をセット。会社名の再確認は現状維持）。
物理削除は柱Bの自動バッチのみが行う（人の操作からは物理削除できなくする）。

### 柱B：物理削除の自動化 — Supabase `pg_cron`

Vercel Cron（HTTPエンドポイントを外部から叩く方式）ではなく、**Supabase純正の `pg_cron`**を
提案します。理由：
- HTTPエンドポイントを晒さない（叩かれる/漏れる/認証トークン管理のリスクがゼロ）
- Vercel側のデプロイ・環境変数・Cron実行枠に依存しない（Hobbyプランの制約も回避）
- 削除ロジックがDB関数として1箇所に閉じ、`purge_expired_rate_limits()`（既存の
  レート制限クリーンアップ関数）と同じ設計パターンを踏襲できる

```sql
-- 0007_tenant_cancellation.sql に含める（Supabaseでpg_cron拡張の有効化が前提）
create extension if not exists pg_cron;

create or replace function purge_cancelled_companies()
returns integer
language plpgsql
security definer
as $$
declare
  rec record;
  purged integer := 0;
begin
  for rec in
    select id, name from companies
    where status = 'cancelled'
      and cancelled_at is not null
      and cancelled_at <= now() - interval '30 days'
  loop
    begin
      -- 削除前に記録（company_idはFKがset nullなので、詳細をdetailsに退避）
      insert into admin_audit_log (action, details, actor_type)
      values (
        'system_company_purge',
        jsonb_build_object('company_id', rec.id, 'company_name', rec.name, 'purged_at', now()),
        'system'
      );

      delete from companies where id = rec.id; -- 子テーブルはCASCADEで自動削除
      purged := purged + 1;
    exception when others then
      insert into admin_audit_log (action, details, actor_type)
      values (
        'system_company_purge_failed',
        jsonb_build_object('company_id', rec.id, 'error', sqlerrm),
        'system'
      );
    end;
  end loop;
  return purged;
end;
$$;

-- 毎日 深夜3:00 JST(=18:00 UTC) に実行
select cron.schedule(
  'purge_cancelled_companies_daily',
  '0 18 * * *',
  $$select purge_cancelled_companies();$$
);
```

1社ずつ例外処理するため、**1社の削除失敗が他社に波及しない**。失敗は
`system_company_purge_failed` として残り、運営者が後日 `admin_audit_log` を見て手動対応できる。

### 柱C：ログ

`admin_audit_log` を使う（新規テーブルは不要）。`AuditAction` 型（`src/lib/audit-log.ts`）に
以下を追加：`super_company_cancel`（解約操作）／`system_company_purge`／
`system_company_purge_failed`。既存の `super_company_delete` は「即時物理削除」の意味を
持たなくなるため、実装時に呼び出し元（DELETEハンドラ）を `super_company_cancel` に置き換える。

## 2. 運用フロー（Before / After）

**Before（危険）**：解約 → 運営者が手動でSupabase SQL Editorを開きDELETE文を書いて実行、
または `DELETE /api/superadmin/companies/[id]` で即座に物理削除。取り消し不可・猶予なし。

**After**：
1. 解約が決まったら、運営画面（`/superadmin/companies/[id]`）で「解約」操作
   → `status='cancelled'`, `cancelled_at=now()` がセットされるだけ（**物理削除ではない**）。
2. 解約直後から、当該契約者・利用者は一切ログイン・打刻・体調報告ができなくなる（柱A）。
3. 30日以内に契約者から連絡があれば `status` を `active` に戻すだけで復旧できる
   （物理削除がまだ走っていないので**完全に可逆**）。
4. 30日経過すると、`pg_cron` が毎晩自動でチェックし、対象があれば物理削除＋ログ記録（柱B・C）。
5. 運営者は何もしなくてよい。`admin_audit_log` で実行履歴を確認できる。
