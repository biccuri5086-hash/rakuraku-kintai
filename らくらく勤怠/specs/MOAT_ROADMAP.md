## 0. 前提：何が堀で、何が堀でないか

| 区分 | 内容 |
|---|---|
| 堀ではない（＝入口） | LINE/GPS打刻・UI・価格の安さ。大手が数ヶ月で追随可能。差別化の入口としてのみ使う |
| 堀になる（＝資産・構造） | ①スイッチングコスト ②派遣法特化 ③専有データ ④ネットワーク効果 ⑤埋め込み ⑥信頼/実績 |

入口で時間を稼ぎ、その時間を①〜⑥へ変換していく。

## 2. Phase B（＝スイッチングコストの中核）

`PHASE_A_派遣モデル設計.md` §6 で Phase B と定義済みの範囲を、堀の観点で優先度づけ。

1. **給与エクスポート**（最優先）
   - `attendance`＋`shifts`＋`assignments` から月次タイムシートを集計
   - 残業/割増/休憩控除の計算、CSV/給与ソフト向けフォーマット出力
   - → 「勤怠が給与計算の起点」になり、剥がすと業務が止まる
2. **派遣先への勤怠報告書の自動生成**
   - `clients`（派遣先）単位で就業実績を帳票化
   - → 派遣先との業務フローに食い込む
3. **月次締め（タイムシート確定）UI**
   - `shifts.status` を confirmed→done で締める運用

※ いずれも **DBマイグレーションを伴う（=要オーナー承認＋ハヤト/ノアのダブルチェック）**。
   マイグレーションは既存方針どおり additive（`create table/add column if not exists`）で非破壊。

## 3. Phase C（＝カウンターポジショニングの本丸）

汎用勤怠SaaS（KING OF TIME / ジョブカン / Touch On Time）が構造的に手を出しにくい領域。

1. **抵触日・3年ルールの自動アラート**（`clients.teishokubi` は Phase A で列だけ用意済み）
2. **派遣元／派遣先 管理台帳の自動生成**
3. **36協定・同一労働同一賃金**対応

※ 実顧客の要件が固まってから着手（`PHASE_A` §6 準拠）。

## 4. 信頼・セキュリティを「実績」に変える（横断・随時）

既に実装/運用済みの資産を、営業で見せられる証跡に変換する。

- 実装済：RLS（`company_id` スコープ）、電話番号暗号化、監査ログ（`SUPABASE_ADD_AUDIT_LOG.sql`）、
  レート制限（`RATE_LIMIT_TABLE.sql`）、ハヤト/ノアのダブルチェック体制
- 変換先：Pマーク/ISMS 等の認証準備、導入社数・解約ゼロ実績、`SECURITY_REPORT.md` の対外版

## 5. データ資産・ネットワーク効果（中長期）

- ③ コンディション報告×稼働履歴 → 離職予兆スコア（本質価値＝離職防止に直結）
- ④ 単発スタッフの共有プール＋評価スコア → 両面ネットワーク。SaaSからインフラへ
